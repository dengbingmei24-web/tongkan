# Feature Specification: 单方面解绑与独立归档选择

**Feature Branch**: `codex/TK-001-unilateral-unbind`
**Created**: 2026-08-14
**Status**: Ready for Planning
**Input**: 任意一方可以单方面解绑；解绑后双方分别决定是否保留旧双人空间，只有双方都删除时才物理删除共同数据。

## User Scenarios & Testing

### User Story 1 - 发起方立即结束绑定 (Priority: P1)

已绑定用户可以在二次确认后单方面解除当前唯一好友关系，并在提交前选择为自己保留只读旧空间或删除自己的访问权。另一方不需要在线或同意，双方解绑后都能立即绑定新的好友。

**Why this priority**: 这是结束关系和释放唯一好友约束的核心能力，没有它就无法安全继续双人空间开发。

**Independent Test**: 使用两个已绑定测试账号，让账号 A 选择保留并解绑；确认 A/B 都不再显示活动绑定，A 显示只读归档，双方都能创建新的好友邀请。

**Acceptance Scenarios**:

1. **Given** 两个账号处于活动绑定，**When** 任意一方确认解绑并选择保留，**Then** 活动关系立即结束，发起方获得只读归档，另一方进入待选择状态。
2. **Given** 发起方选择删除，**When** 解绑成功，**Then** 发起方不能再访问旧空间，另一方仍能独立决定保留或删除。
3. **Given** 解绑请求正在处理，**When** 用户重复点击，**Then** 只执行一次解绑且界面显示明确加载状态。

---

### User Story 2 - 另一方独立决定数据去留 (Priority: P1)

未发起解绑的一方在下次进入“我们”页时看到旧空间待选择提示，可以独立选择保留只读归档或删除自己的访问权，发起方无法代替其决定。

**Why this priority**: 共同数据不能被单方删除，是已确认的数据所有权边界。

**Independent Test**: 账号 A 解绑后，账号 B 重启 App 并选择与 A 不同的决定；确认双方可见状态互不覆盖。

**Acceptance Scenarios**:

1. **Given** 另一方尚未选择，**When** 其登录或刷新“我们”页，**Then** 显示原好友、解绑日期和保留/删除选项。
2. **Given** 一方选择保留、另一方选择删除，**When** 两边刷新，**Then** 保留者继续看到只读归档，删除者看不到旧空间。
3. **Given** 双方均选择删除，**When** 第二个删除决定提交成功，**Then** 旧双人空间底层数据被物理删除且双方均不可恢复访问。

---

### User Story 3 - 保留归档并开始新关系 (Priority: P2)

选择保留的用户可以在“我们”页查看旧空间摘要，旧空间只读且与新的活动好友关系完全分离。

**Why this priority**: 证明保留选择有实际价值，同时避免旧关系影响新关系。

**Independent Test**: 用户保留旧归档后绑定新好友；确认新活动空间和旧只读归档同时可见但不能互相写入。

**Acceptance Scenarios**:

1. **Given** 用户保留了旧空间，**When** 查看归档列表，**Then** 显示原好友昵称、绑定日期、解绑日期和只读状态。
2. **Given** 用户已有旧归档，**When** 绑定新好友，**Then** 新关系正常创建且旧归档不参与邀请、片库写入或共同观看统计。

### Edge Cases

- 两端几乎同时发起解绑时，只允许一个事务成功，另一个收到关系已变化提示。
- 解绑时另一方离线、Session 过期或没有推送权限，不影响解绑事务。
- 用户提交不属于自己的 `pairId`、重复提交删除决定或访问已物理删除归档时，返回明确且不泄露关系信息的错误。
- 网络超时后客户端刷新服务端状态，不根据本地点击结果假定解绑成功。
- 旧 pair 的超时请求在用户已经绑定新好友后到达时，必须因 `pairId` 不匹配而失败，绝不能解绑新关系。
- 当前仅有关系元数据、尚未实现片库/日历/历史表时，保留策略仍必须为未来子表提供稳定的级联和访问边界。

## Requirements

### Functional Requirements

- **FR-001**: 系统 MUST 允许活动绑定中的任意一方在二次确认后单方面解绑。
- **FR-002**: 解绑 MUST 原子地把关系标记为已解绑并释放双方唯一活动好友约束。
- **FR-003**: 发起方 MUST 在解绑请求中提交当前活动关系的 `pairId` 并选择 `keep` 或 `delete`；服务端只可解绑该精确 pair，未提供有效目标或选择时不得解绑。
- **FR-004**: 另一方 MUST 获得独立的待选择状态，发起方不得替其写入保留决定。
- **FR-005**: 归档记录仍存在时，同值 `keep/delete` 重试 MUST 返回当前结果，异值重试 MUST 返回决定已冻结；双方删除触发物理清理后，同一 `pairId` 的后续请求 MUST 返回与未知归档相同的 404，客户端通过刷新列表收敛为已完成状态。
- **FR-006**: 选择 `keep` 的用户 MUST 只能读取旧空间，不得修改旧片库、日历、历史、统计或发送旧关系邀请。
- **FR-007**: 选择 `delete` 的用户 MUST 立即失去旧空间访问权。
- **FR-008**: 只有双方都处于 `delete` 时，系统 MUST 物理删除 pair 及其全部子数据。
- **FR-009**: 双方在解绑事务成功后 MUST 可以立即创建或接受新的好友邀请。
- **FR-010**: 查询好友状态 MUST 同时返回活动关系、待选择旧空间和当前用户可见的只读归档摘要。
- **FR-011**: Android “我们”页 MUST 提供可发现的解除绑定入口、二次确认、保留选择、加载、成功和失败状态。
- **FR-012**: Android MUST 在服务端确认成功后清除活动好友 UI；网络不确定时通过刷新恢复权威状态。
- **FR-013**: 未发起方下次登录、恢复会话或进入“我们”页时 MUST 看到待选择提示。
- **FR-014**: 解绑和归档 API MUST 只允许当前 Session 所属用户操作自己的活动关系或归档成员记录。
- **FR-015**: 解绑不得退出账号、删除账号、撤销设备 token 或影响匿名临时房间能力。
- **FR-016**: 首版不要求推送解绑通知；有推送时只能作为提示，权威状态仍来自账号 API。
- **FR-017**: 解绑事务成功时 MUST 立即使双方所有未使用的好友邀请码失效。
- **FR-018**: `pendingArchives` 和 `archives` MUST 按 `unboundAt` 倒序、`pairId` 升序稳定返回；Android MUST 先显示全部待选择卡，再显示保留归档。
- **FR-019**: 归档摘要中的原好友昵称、头像和脱敏邮箱 MUST 使用解绑时快照，不随对方后续资料修改而变化。

### Key Entities

- **Pair**: 双方的历史关系；活动时可写，解绑后冻结，双方均删除时物理删除。
- **Pair Archive Member**: 每个 pair 与用户的一条独立保留记录，状态为 `pending`、`keep` 或 `delete`，并保存解绑时的对方公开资料快照。
- **Archive Summary**: 当前用户可见的只读摘要，包含 pairId、原好友、绑定/解绑时间和保留状态。

## Assumptions

- `keep` 用户后续主动删除旧归档属于后续能力；本试点只处理解绑时或待选择提示中的首次决定。
- 尚未实现的片库、日历、历史和统计表未来都以 `pair_id` 关联，并在 pair 物理删除时级联删除。
- 解绑成功后的系统分享、FCM 设备 token 和房间 Session 不需要自动清理，因为它们不代表好友关系本身。

## Success Criteria

- **SC-001**: 两个测试账号在 30 秒内完成单方解绑、双方状态刷新和新邀请码创建。
- **SC-002**: 20 次并发或重复解绑测试中不会出现用户仍占用活动关系、双方状态不一致或重复归档记录。
- **SC-003**: 一方保留、一方删除时，100% 的访问检查符合各自决定且互不覆盖。
- **SC-004**: 双方删除后，服务端查询不到 pair、归档成员和关联子数据。
- **SC-005**: Android 重启后能从服务端恢复活动关系、待选择或归档状态，不依赖旧页面内存。
- **SC-006**: 解绑前创建的双方邀请码在解绑后 100% 无法被接受。
