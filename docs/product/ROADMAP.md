# 同看产品路线图：Now / Next / Later

> 本路线图把已经确认的产品目标、用户证据和工程约束整理为阶段方向，用于排序和取舍，不是固定发布日期承诺。候选工作仍需在进入开发前形成具体规格与验收标准。

## 1. 路线图口径

- **Now**：当前生产版本的真实双人使用闭环仍是质量门槛；用户可以选择延期，但延期不等于通过。
- **Next**：在不覆盖既有风险的前提下，继续规划已确认的下一项长期价值能力。
- **Later**：保留已确认的长期方向和待探索能力，不承诺顺序、版本号或日期。
- **待确认**：缺少直接用户证据、范围选择或发布条件，不能视为已承诺功能。

当前依据包括：用户已确认 Alpha 10.2.4 可以成功解除好友、Alpha 10.3 Breath Tech 视觉真机验收通过；此前真实使用暴露过退出/重新登录、匿名与账号模式切换、好友解绑、邀请链路、片库命名和封面等问题。用户于 2026-09-01 明确选择暂不执行剩余双设备验收并继续规划开发；产品长期边界仍是唯一好友、最多两人、匿名房间保留、B站视频不经同看服务端中继。

## 2. Now：真实使用闭环与稳定性

**阶段目标**：让当前 Alpha 10.3 生产能力从“功能已经上线”变成“双方可以放心日常使用”。结束时间不预设，以双设备物理证据为准。当前状态为用户主动延期，不是通过或取消。

### 要解决的问题

- 历史问题多次表现为“界面有入口，但操作没有真正完成”，需要用真实设备验证端到端结果，而不是只依赖自动化测试。
- 好友解绑已经由用户确认成功，但保留片库与删除片库两条归档路径仍缺少完整双设备物理矩阵。
- 一方创建房间后，另一方能否无需通知、无需复制链接，直接从 App 首页发现并进入，仍需生产环境物理验证。
- 登录、退出、重新登录、匿名模式与账号模式切换需要持续稳定，不能让用户陷入不可恢复状态。
- 片库已经支持添加、命名、封面和播放，但仍需验证这些数据在重启、重登和双方共同使用后保持正确。

### 预期用户结果

- 用户可以可靠退出、重新登录，并在匿名模式与账号模式之间自由切换。
- 用户可以解除好友，并明确选择保留或删除自己的双人空间归档；双方结果互不越权。
- A 在 App 内创建房间后，B 可以在首页看到可进入的房间，不需要 A 发送链接；通知只负责提醒，不是进入房间的前提。
- 片库中的视频有可识别名称和封面，B23 链接添加失败时能看到明确、可恢复的原因。
- 网络波动、房主离开、房间替换或权限失败时，界面给出明确状态，不留下失效入口。

### 候选工作

- 完成双设备生产验收：好友房间首页卡片、创建者不显示自己的卡片、10 秒内发现、直接加入、房主离开后清理、新房替换旧房。
- 补验解绑的保留归档、删除归档、双方独立 retention、重新绑定后的访问边界。
- 回归退出/重新登录、账号与匿名模式切换、会话恢复和完整登录表单重置。
- 回归片库命名、JPEG 封面、B23 添加、分类展示、房间内选片和重启后的数据一致性。
- 只修阻断日常使用的 P0/P1 问题；不在本阶段扩展好友列表、多人房间或新的社交系统。
- 建立最小生产运维闭环：备份、回滚、关键接口健康检查和必要的错误记录。
- Release 签名、公开下载渠道和面向非自用用户的分发标准：**待确认**。

### 进入 Next 的建议条件

- 双设备物理验收证明“解绑、模式切换、App 内发现并加入好友房间、片库核心操作”均可重复完成。
- 未发现阻断日常使用的数据丢失、越权访问或不可恢复登录问题。
- 剩余问题可以被明确降级为非阻断项，并记录到 QA 清单。

## 3. 已实现但待补验：观看日历与“今天想看”

**实现版本**：Alpha 10.3。发布日期：**待确认**。

**当前状态（2026-09-01）**：Account/D1、Android 与 QA 已集成并通过自动化门禁；Preview/生产 migration 0007 与 Worker、Preview 16-case Live QA、Alpha 10.3 生产配置 Debug APK 和 Breath Tech 视觉真机验收均已完成。用户选择暂不执行双设备日历/日常使用验收；release 签名、push 和公开发布仍未执行。这不降低任何发布门槛，也不构成发布日期承诺。

### 要解决的问题

- 双人片库解决了“以后看什么”，但没有解决“哪一天一起看”。
- 双方仍需要在 App 外反复沟通时间，计划与真正开始观看之间缺少直接入口。

### 预期用户结果

- 双方可以为片库视频安排日期；日期必填，开始时间和备注可选。
- 首页可以直接看到“今天想看”，并从计划进入创建房间或加入同看。
- 任一方可以新增、改期或取消计划，另一方看到一致结果。
- 解绑后，计划数据继续遵循双方独立保留或删除归档的规则。

### 已完成的本地切片与待验证工作

- 已本地实现共享日历数据模型、独立 revision、版本冲突和活动 pair/归档授权边界。
- 已本地实现月历、日期详情、计划新增/编辑/完成/取消、片库快速安排和首页“今天想看”。
- 已明确首版只安排当前共同片库视频，并保存媒体快照；未来是否支持尚未入库的视频：**待确认**。
- Preview/生产 migration 0007 与 Worker、A/B/C Live QA、Alpha 10.3 APK 构建和 Breath Tech 视觉真机验收已完成；进入真实交付前仍需完成双设备日历/日常使用验收，并另行决定 release 签名、push 与公开发布。
- 自动提醒、重复计划和外部日历同步不作为 Next 默认范围；是否开发：**待确认**。
- 实际共同观看记录、日历双标记和统计已在 Alpha 10.4 本地集成，但不随 Alpha 10.3 自动进入 Preview、生产或 APK。

### 主要依赖

- 登录、好友关系、片库和归档规则已被复用，但 Now 的双设备生产证据仍未补齐。
- Account Worker 与 D1 的计划能力已在 Preview 和生产启用，并继续与 Signaling Worker 隔离；后续变更仍需分别取得 migration 和 Worker 部署授权。
- Android 首页已同时容纳“好友正在看”和“今天想看”，视觉真机验收已通过；信息刷新、从计划进入房间和双设备一致性仍需矩阵验证。

## 4. Next：共同观看历史与统计（本地已集成）

**候选版本**：Alpha 10.4。本地实现、审查和集成已于 2026-09-01 完成；Preview/生产 migration、部署、APK、发布时间和公开发布方式仍为 **待确认**，不承诺固定交付日期。

### 4.1 要解决的问题

- 用户可以计划和进入房间，但无法回顾双方真正一起看过什么、看了多久。
- 缺少“计划”和“实际观看”之间的闭环，也无法形成长期共同记忆。
- 统计必须来自服务端可验证的双人有效播放重叠，不能由任一手机自行累计或把匿名房间误记入账号空间。

### 4.2 预期用户结果

- 只有双方同时在线且视频实际播放时才累计共同观看记录。
- 用户可以查看历史列表、月度观看时长、观看次数和最近同看日期；完成数量在首切片保持隐藏，后续是否展示为 **待确认**。
- 日历可以区分计划与实际观看记录。
- 解绑后，历史和统计继续遵循独立归档规则。

### 4.3 本地已完成切片

- **P0 可信记账链路（已本地实现）**：账号服务为当前 pair/room 签发短期历史授权；Signaling Durable Object 依据双方连接、权威播放状态、最新播放器报告、缓冲和媒体一致性生成服务端观看区间；匿名或只有一方授权的房间不计入。
- **P0 历史与月度摘要（已本地实现）**：Account D1 幂等接收区间，提供历史列表、本月共同观看时长、观看次数和最近同看日期；统计故障不得阻断房间播放。
- **P1 日历实看标记（已本地实现）**：月历区分计划标记与实际观看标记，日期详情将“计划”和“一起看过”分区；实际记录不自动修改计划状态。
- **P1 归档只读（已本地实现）**：keep 旧空间可查看历史和统计，pending/delete/第三方拒绝，双方 delete 后随 pair 级联清理。
- **已冻结首切片**：满 60 秒才进入可见历史；完成状态保持 unknown 并隐藏完成数；UTC 存储 + 当前设备 offset；不关联或自动完成计划；跟随 pair keep/delete，暂不做单条删除、纠错或导出。
- **本地审查证据**：Protocol 13 项、Account 93 项、Signaling 67 项测试通过；Android 单元测试与 Lint、History QA 14 cases/13 tags ValidateOnly 通过。APK、Preview/生产 Live QA 和全仓剩余门禁仍待单独执行。

### 4.4 主要依赖与取舍

- Signaling 负责可信播放重叠和重试队列，Account 负责身份授权、D1 持久化、聚合与访问控制；Android 只传递短期授权并周期上报真实播放器状态，不自行计算最终时长。
- 使用独立短期 room grant 关联账号与临时房间；不把 Session Token、邮箱、房间 host key 或 invite key 写入历史记录。
- 第一切片只统计登录且绑定好友、通过 App 活跃房间链路建立的 B站房间；匿名、手工分享给第三方、屏幕共享和 direct-video 默认不计入。
- 历史写入采用追加/幂等模型，不复用片库或日历 revision；读取失败只影响历史页面，不影响房间、聊天、播放和邀请。
- Alpha 10.3 的延期验收仍是独立发布风险；Alpha 10.4 的规划或实现不能反向把它标记通过。

## 5. Later：长期自用与 1.0 稳定性

#### 要解决的问题

- 当前版本仍是 Debug 签名，且真实设备、网络和长时间播放矩阵尚未完全覆盖。
- 长期使用需要可升级、可恢复、可诊断，而不只是单次安装可用。

#### 预期用户结果

- 双方在常见网络切换、进后台、横竖屏、重连和长时间播放场景下仍能稳定使用。
- 升级不会破坏账号、好友关系、片库、计划或历史数据。
- 出现生产故障时可以备份、回滚并定位关键问题。

#### 候选工作

- 扩展双设备、FCM、网络切换、重连、横竖屏、聊天和长时间播放验收矩阵。
- 建立 Release 签名、版本升级兼容、生产备份恢复和最小监控方案。
- 1.0 定位为两人长期自用版本还是可公开发行版本：**待确认**。
- 支持设备范围、网络条件和连续播放时长门槛：**待确认**。

### 5.1 探索项

以下能力目前证据不足或不属于已确认核心闭环，全部为 **待确认**：

- 自动提醒、重复计划和外部日历同步。
- 正式内置头像资源；自定义头像上传仍不是已确认范围。
- B站登录、高清画质或 Cookie 相关能力。
- 屏幕共享、TURN 和复杂网络诊断。
- 历史导出或管理后台。

## 6. 主要取舍

- **稳定性优先于功能数量**：先消除“按钮存在但链路不闭环”的问题，再增加新模块。
- **App 内发现优先于通知送达**：好友房间必须能从首页进入；FCM 只做提醒和加速。
- **日历先于统计**：时间协调是当前更直接的问题，计划数据也为后续“计划与实际”统计提供结构。
- **双人空间优先于社交扩张**：唯一好友、最多两人是核心约束，不用好友列表、群聊或社区稀释产品价值。
- **最小数据收集**：不保存、代理或转发 B站视频流，不上传 B站账号、密码或 Cookie。
- **个人自用优先于公开分发**：在发布对象没有确认前，不为了应用商店或广泛兼容提前增加复杂度。

## 7. 依赖顺序

建议依赖顺序为：

`Alpha 10.3 双设备验收延期但保留 → TK-005 Alpha 10.4 本地实现与审查完成 → Preview migration/部署与 Live QA → 另行决定生产与 APK → Later 1.0 稳定化`

Alpha 10.3 的本地实现、真实环境部署和视觉验收已完成，但这不是固定版本排期，也不表示已公开发布。TK-005 统计口径已按 D-092 冻结，本地实现与审查已完成，当前等待 Preview 门禁；如果后续双设备矩阵发现新的 P0/P1，必须重新评估并优先修复基础能力。

## 8. 明确不进入当前路线图

- 多人房间。
- 好友列表和多好友关系。
- 群聊、社区、动态广场和公开主页。
- 推荐、排行榜、等级和付费会员。

如未来希望改变这些边界，需要新的用户证据、产品决策和架构评估，不能从本路线图直接推导为承诺。
