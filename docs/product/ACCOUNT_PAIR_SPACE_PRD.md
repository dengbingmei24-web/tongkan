# 同看账号与双人空间 PRD

> 状态：Alpha 10.0–10.2 已实现并投入生产日常使用；Alpha 10.3–10.4 待开发
> 创建日期：2026-08-11
> 目标里程碑：Alpha 10 起
> 真源关系：账号、唯一好友、双人历史、日历计划和云端片库以本文为准；播放器与房间稳定性仍以 `docs/product/ANDROID_FOLLOWUP_PRD.md` 为准。

## 1. 背景

同看最初是“无注册、临时房间、两个人同步播放”的轻量工具。随着真实使用，产品目标扩展为一个长期双人空间：两个人绑定后，不仅能快速开始同看，还能共同维护想看的内容、安排观看日期、回顾已经看过的视频，并看到每月一起观看的时长。

本次范围明确把“同看账号系统”放在 B站高清登录之前。B站画质优化暂缓，不阻塞账号与双人空间开发。

## 2. 已确认产品决策

1. 同看建立自己的账号系统，第一版采用邮箱 + 验证码登录。
2. 一个账号同时只能绑定一个好友，产品不提供好友列表、群组或多人关系。
3. 两个绑定用户组成一个长期“双人空间”。
4. 双人空间保存共同观看历史，并提供月度观看时长等统计。
5. 提供观看日历，可记录预计在哪一天观看哪个视频。
6. 当天计划的视频出现在首页“今天想看”列表中。
7. 提供长期片库，可保存想看的 B站视频并分类、排序和选择播放。
8. B站账号登录与画质选择后置，不进入账号系统第一阶段。
9. Alpha 10.0 首版使用指定 QQ 邮箱账号通过 SMTP 发送同看验证码；用户登录邮箱不限定为 QQ 邮箱。
10. 保留“匿名临时房间”入口；未登录用户仍可创建或加入临时房间，但不能使用云端好友、片库、日历、历史和统计。
11. 绑定关系允许任意一方单方面解绑；解绑后双方分别决定是否保留自己可见的片库、日历、历史与统计归档，任何一方都不能替另一方删除数据。
12. 活动双人空间的片库完全共享，双方拥有相同的查看、添加、分类、排序、安排和删除权限，第一版不提供个人私密片库。
13. 第一版只使用内置头像，不支持用户上传；头像图片由用户后续提供并作为 App 资源包接入。
14. 共同观看时长采用类似“一起听时长”的双人有效播放重叠模型，只累计双方在同一房间同时在线并实际播放的自然时间。
15. 日历计划采用“日期必填 + 开始时间可选 + 备注可选”；自动提醒和重复计划不进入第一版。

## 3. 产品目标

- 从“每次创建临时房间”升级为“打开 App 就进入两个人的长期空间”。
- 绑定后减少邀请链接操作，优先一键开始或加入好友的同看房间。
- 把“想看、计划看、正在看、已经看”形成完整闭环。
- 让历史统计表达两个人真正共同观看的时间，而不是简单累加单端播放器时长。
- 保留现有同步播放器、手动横屏、独立全屏、弹幕、倍速和稳定性能力。

## 4. 第一版非目标

- 一个人绑定多个好友。
- 好友列表、群聊、动态广场、公开主页或内容推荐社区。
- 向同看服务器上传 B站账号、密码或 Cookie；同看邮箱验证码只用于同看身份验证。
- 同步双方画质设置。
- 自动抓取、代理、下载或重新分发 B站视频流。
- 复杂成就、等级、付费会员、排行榜或公开数据分享。

## 5. 推荐信息架构

登录并完成好友绑定后，Android 主界面使用 4 个底部入口：

| 入口 | 主要内容 | 高频操作 |
|---|---|---|
| 首页 | 好友状态、开始同看、今天计划、继续观看、月度摘要 | 开始同看、播放今天计划 |
| 片库 | 双人共享视频、分类、搜索、排序、添加链接 | 添加、分类、安排日期、播放 |
| 日历 | 月历、计划标记、实际观看记录、选中日期详情 | 新建计划、改期、查看当天历史 |
| 我们 | 两个人的资料、绑定天数、月度统计、历史入口、账号设置 | 查看统计、管理绑定、退出登录 |

观看页是独立沉浸页面：进入视频后隐藏底部导航，返回时回到发起播放的首页、片库或日历位置。

### 5.1 未登录状态

- 显示品牌、邮箱输入、获取验证码、验证码输入和登录按钮。
- 首次登录后设置昵称；头像第一版只从内置头像中选择，不提供图片上传。头像资源由用户后续提供，在资源到位前可使用颜色种子占位。
- 保留“暂时使用匿名房间”作为次要入口；账号功能不可用，并明确提示匿名数据不会同步到云端。

### 5.2 未绑定好友状态

首页主体替换为“绑定你的唯一好友”：

- 生成一次性绑定邀请码、链接或二维码。
- 粘贴对方邀请码并确认绑定。
- 明确提示“每个账号只能绑定一位好友”。
- 对方已有好友时返回自然语言错误，不允许覆盖原绑定。

### 5.3 已绑定首页

推荐从上到下排列：

1. 顶部双人状态：双方头像、昵称、在线状态。
2. 主按钮：“开始同看”或“加入好友的房间”。
3. 今天想看：展示当天计划的视频卡片，最多先露出 3 条。
4. 继续观看：最近一次未完成视频及进度。
5. 本月一起看：观看时长、次数和看完视频数的紧凑摘要。

首页不放完整月历和完整片库，避免首屏变成信息面板。

## 6. 核心功能

### 6.1 邮箱账号

推荐第一版：

- 邮箱地址去除首尾空格并使用规范化小写形式作为账号索引。
- 验证码有效期 5 分钟；同一邮箱 60 秒内不能重复发送。
- 验证码、会话令牌只存哈希；服务端不保存明文验证码。
- 邮箱使用不可逆 HMAC 索引；界面仅展示脱敏邮箱，例如 `d***@example.com`。
- “我们”页显示用户昵称、脱敏邮箱和稳定的同看用户 ID；昵称允许修改并同步到账号服务，长度为 1–24 个字符。
- 房间与消息默认使用账号昵称；匿名房间继续使用入口页填写的临时昵称。
- Android 登录令牌存入 Android Keystore 保护的本地存储，不继续放普通 SharedPreferences。
- 支持登录、刷新会话、退出当前设备、退出全部设备和注销账号。

Alpha 10.0 首版使用指定 QQ 邮箱账号通过 SMTP 发送验证码。服务端只使用 QQ 邮箱生成的 SMTP 授权码，不保存或使用邮箱登录密码；邮箱地址、授权码、主机和端口全部通过 Cloudflare Secret/环境变量配置。邮件发送封装为可替换适配器，后续若触发个人邮箱频率限制，可在不改变登录 API 的情况下切换到事务邮件服务。开发环境可以使用明确标记的测试验证码，但测试模式不得进入公开生产环境。

### 6.2 唯一好友绑定

服务端必须强制保证每个用户最多只有一个活动绑定：

- 邀请码一次性使用并在 24 小时后过期。
- 接受邀请时服务端原子检查双方都未绑定。
- 绑定成功后创建唯一 `pairId`。
- 所有片库、计划、历史和统计都归属 `pairId`，而不是临时房间。
- 任何一方都不能在不解绑的情况下添加第三个人。

任意一方可以在“我们”页发起解绑，二次确认后立即解除活动关系并释放双方的唯一好友名额。解绑后的数据规则：

- 原双人空间立即停止新增和修改，转为历史归档状态。
- 发起方在确认解绑时选择“保留我的归档”或“删除我的归档”。
- 另一方下次打开 App 时收到解绑提示，并独立选择是否保留自己的归档。
- 选择保留后，可查看只读的旧片库、日历、共同历史和统计；不能继续共同编辑，也不能写入新的观看记录。
- 选择删除后立即失去访问权限；只有双方都选择删除时，服务端才物理删除该双人空间数据。
- 任意一方均不能替对方选择、删除或覆盖对方的归档权限。
- 解绑完成后双方都可以重新绑定新的唯一好友。

### 6.3 一键同看

第一阶段保留现有 Durable Objects 房间同步内核：

- 用户点击“开始同看”，后端仍创建临时房间。
- 创建结果与 `pairId` 关联，好友打开 App 后首页显示“好友正在等你”。
- 好友点击即可加入，不再要求手动粘贴邀请链接。
- 原分享链接继续作为兼容和故障恢复入口。
- 房间运行状态仍然临时；账号系统只保存房间摘要和观看结果，不把房间永久化。

### 6.4 完全共享的双人片库

第一版片库完全共享：

- 双方看到完全一致的片库、分类和排序结果，并拥有相同的添加、编辑、安排和删除权限。
- 任一方可添加 B站链接；条目保留添加者和最后修改者，便于解释操作来源。
- 第一版不提供个人私密片库，也不提供“只对我可见”分类。
- 自动保存 BVID/分P、标题、封面、UP 主、时长和添加者快照。
- 支持自定义分类，例如“电影”“纪录片”“动画”“下饭”“以后再看”。
- 默认分类：全部、未观看、已计划、已看完。
- 支持搜索、筛选、显式排序模式和长按拖动。
- 每个视频提供：立即播放、安排日期、修改分类、标记看完、删除。
- 从日历添加陌生视频时，先自动进入片库，再创建计划。
- 切换视频后仍遵循已确认规则：停在 0 秒，等待用户手动播放，不自动连播。

### 6.5 观看日历

日历计划至少包含日期；还可以选择以下信息：

- **开始时间**：可选，例如“20:00”；不填写时显示“当天”。
- **备注**：可选，例如“吃完饭一起看”或“看完第一集”。
- **提前提醒**：可以支持当天、提前 10 分钟或提前 30 分钟，但需要 Android 通知权限与可靠调度。
- **重复计划**：例如每周六，当前双人自用场景价值较低。

Alpha 10.3 第一版确定采用“日期必填 + 开始时间可选 + 备注可选”，自动提醒和重复计划后置。

- 月视图中，空心点表示有观看计划，实心点表示当天有实际共同观看记录；两者同时存在时显示双标记。
- 点击日期后在下方显示“计划观看”和“实际观看”两个分组。
- 计划支持改期、取消、标记完成和直接开始同看。
- 首页只读取今天和最近日期，不复制整个月历。
- 未填写开始时间的计划按全天计划展示；填写时间后按时间排序。
- 自动提醒和重复计划放到后续小版本。

### 6.6 共同观看历史

历史记录必须由服务端根据房间状态生成，不能只相信客户端上报。共同观看时长采用“双人有效播放区间重叠”模型：

- 只有已绑定双方进入同一个关联 `pairId` 的房间、都在线、都已准备完成且房间处于实际播放状态时才开始计时。
- 从双方条件同时满足的较晚时刻开始，到任一方暂停、缓冲、离线、离开、播放结束、解绑或切换视频的最早时刻结束。
- 暂停、缓冲和离线时间不计入；短暂重连可合并为同一历史段，但断线秒数不能补算。
- 按真实自然时间累计，不按视频进度累计；使用 2 倍速共同播放 60 秒，统计仍增加 60 秒，而不是 120 秒。
- Seek 不会增加或扣减时长；同一墙钟时间段只计算一次，不把两台设备时长相加。
- 匿名临时房间不写入账号共同观看统计。
- 保存视频快照、开始时间、结束时间、共同观看秒数、是否看完和发起人。

### 6.7 统计与“我们”页面

第一版统计：

- 本月共同观看总时长。
- 本月共同观看次数。
- 本月看完的视频数。
- 最近一次同看日期。
- 历史累计共同观看时长。
- 可选：连续有观看记录的月份，不做公开排行榜。

统计只展示给绑定双方。

### 6.8 设备通知与一起看邀请

- 登录成功、会话恢复、App 回到前台和 FCM token 刷新时，Android 向账号服务注册当前设备；退出账号时注销当前设备 token。
- 服务端只保存 token 的 HMAC 去重索引和 AES-GCM 加密值，不在日志、客户端持久化或上下文文档中记录明文服务端凭据。
- “邀请一起看”只允许通知当前唯一好友，消息包含邀请人昵称、临时房间深链和过期时间，不扩展为群通知、营销通知或公开消息系统。
- 好友点击通知后复用 `/room/{roomId}#join={inviteKey}` 加入流程。
- 好友没有有效设备、拒绝通知权限、Provider 未配置或推送失败时，邀请方自动打开系统分享兜底，不能阻塞房间创建。
- 第一版不提供通知中心、历史通知列表、多设备管理 UI、重复提醒或日历提前提醒。

## 7. 数据模型建议

### 7.1 账号与会话

- `users`：用户 ID、邮箱 HMAC、脱敏邮箱、昵称、头像种子、创建/注销时间。
- `auth_sessions`：用户、令牌哈希、设备名称、过期/撤销时间。
- `email_challenges`：邮箱 HMAC、验证码哈希、过期时间、尝试次数和频率限制信息。
- `device_tokens`：用户、Provider、token HMAC、AES-GCM 密文、设备名称、App 版本、最后活跃与撤销时间。

### 7.2 好友关系

- `pair_invites`：邀请人、邀请码哈希、过期/使用时间。
- `pairs`：双方用户 ID、绑定状态、解绑发起人、绑定/解绑时间。
- `active_pair_members`：`userId` 唯一，用数据库约束保证一个人只有一个活动好友。
- `pair_archive_choices`：旧双人空间、用户、`pending/keep/delete` 选择和决定时间；每个用户独立唯一。

### 7.3 内容与日历

- `library_categories`：双人空间、名称、排序。
- `library_items`：双人空间、媒体身份、元数据快照、分类、排序、状态、添加者。
- `watch_plans`：双人空间、片库项目、计划日期、可选开始时间、可选备注、状态、创建者。开始时间按用户本地时区录入，同时保存标准时间与时区信息以避免跨设备偏移。

### 7.4 历史与统计

- `watch_sessions`：双人空间、房间、视频快照、开始/结束时间、共同观看秒数、完成状态。
- `watch_intervals`：必要时保存合并前的播放区间，用于恢复和审计。
- `daily_pair_stats`：按双人空间和日期聚合时长、次数、完成数，减少月历和月度统计查询成本。

## 8. 后端架构建议

建议新增独立 `apps/account` Cloudflare Worker，而不是把邮箱账号和用户数据直接塞进现有房间 Worker：

- `apps/account`：邮箱验证、QQ SMTP 发信适配器、用户会话、好友绑定、片库、日历、历史和统计。
- Cloudflare D1：保存账号和双人空间关系数据。
- `apps/signaling`：继续负责临时房间、WebSocket 和播放锚点。
- 两个服务通过 Service Binding 校验账号和提交观看摘要。
- Pages 继续提供同域 API 入口，Android 不直接依赖 `workers.dev`。

这样可以把邮箱身份信息与高频房间信令隔离，降低播放器迭代影响账号系统的风险。

## 9. API 草案

### 9.1 账号

- `POST /api/auth/send-code`
- `POST /api/auth/verify-code`
- `POST /api/auth/refresh`
- `POST /api/auth/logout`
- `DELETE /api/account`
- `GET /api/me`
- `PATCH /api/me`

### 9.2 好友

- `POST /api/pair/invites`
- `POST /api/pair/invites/{code}/accept`
- `GET /api/pair`
- `POST /api/pair/unbind`：单方面解绑，并提交发起方的 `keep/delete` 归档选择
- `PUT /api/pair/archives/{pairId}/choice`：另一方或尚未决定者提交自己的保留选择
- `GET /api/pair/archives`：读取当前账号保留的只读旧双人空间
- `GET /api/pair/active-room`
- `POST /api/pair/watch-invites`：向当前唯一好友的活动设备发送房间深链通知。
- `POST /api/devices/register` / `POST /api/devices/unregister`：注册或注销当前账号设备 token。

### 9.3 片库与日历

- `GET/POST /api/library/items`
- `PATCH/DELETE /api/library/items/{id}`
- `GET/POST /api/library/categories`
- `GET/POST /api/calendar/plans`
- `PATCH/DELETE /api/calendar/plans/{id}`

### 9.4 历史与统计

- `GET /api/history`
- `GET /api/stats/monthly?month=YYYY-MM`
- `GET /api/calendar/month?month=YYYY-MM`

## 10. Android 实现建议

继续使用 Java，不引入 Kotlin 或 Compose，但账号功能不应继续全部堆在当前 `MainActivity.java`：

- `AuthActivity`：邮箱验证码登录和首次资料。
- `MainActivity`：四入口底部导航和页面容器。
- `WatchActivity`：迁移或承载现有 WebView 房间观看，专门处理横竖屏和全屏。
- `AccountClient`：账号、好友、片库、日历和历史 REST API。
- `SessionStore`：Keystore 保护的会话令牌。
- 页面继续使用原生 Java View；底部导航用自定义布局，不引入 AndroidX/Material 新依赖。

应先拆出网络和会话层，再迁移观看页，避免一次性重写已经通过真机测试的播放器。

## 11. 安全与隐私要求

- 同看服务器永远不接收 B站密码或 Cookie。
- 邮箱只用于身份验证、账号安全和必要的服务通知，不用于营销。
- 验证码接口按邮箱、IP、设备和时间窗口限流。
- QQ 邮箱 SMTP 授权码只放 Cloudflare Secret，绝不保存邮箱登录密码；日志不得输出授权码或完整验证码。
- 会话令牌可撤销、可过期，不在日志中输出。
- 所有账号 API 只接受 HTTPS。
- 提供账号注销、退出全部设备和好友解绑。
- 解绑归档选择按用户独立授权；服务端不得允许一方删除另一方保留的副本。
- 日历、片库、历史和统计默认只对绑定双方可见。

## 14. 第一阶段验收标准

- 同一邮箱可以通过验证码登录并在重启 App 后恢复会话。
- 验证码过期、输错、频繁发送和会话失效都有自然语言错误和恢复操作。
- 服务端任何路径都不能让一个账号同时属于两个活动好友关系。
- 任意一方可以单方面解绑，解绑后双方都立即恢复可绑定状态。
- 双方分别选择保留或删除自己的旧空间归档；一方的选择不会改变另一方的访问权。
- 只有双方都选择删除后，旧双人空间数据才会被物理删除。
- 绑定双方能看到一致的好友资料和绑定状态。
- 双方看到完全一致的共享片库并拥有相同编辑权限；不存在个人私密片库。
- 用户只能选择内置头像，不能上传自定义图片。
- 共同观看时长只累计双方同时在线且实际播放的自然时间；暂停、缓冲、离线和匿名房间不计入。
- 日历计划必须选择日期，可以不填开始时间和备注；未填时间显示“当天”，填写时间后按时间排序。
- 第一版不提供日历提前提醒和重复计划；好友一起看邀请可以在已配置 FCM 的 Android 构建中请求通知权限。
- 好友位于后台或锁屏时能收到一起看邀请，点击后进入对应房间；无 token、拒绝权限或发送失败时邀请方仍能使用系统分享。
- 未登录用户可以继续创建和加入匿名临时房间，但无法读取或修改任何账号双人空间数据。
- 账号注销和好友解绑不会破坏现有匿名房间同步服务。
- 未完成账号登录时，Alpha 9.3.6 播放器仍可作为独立回退基线。

## Alpha 10.2.4 活跃好友房间

- 登录且已绑定好友的一方创建房间后，房间会在完成 WebSocket 鉴权后自动发布到当前双人空间，默认展示 10 分钟。
- 另一方无需接收通知或复制链接：首页每 10 秒刷新一次，出现“好友正在等你一起看”卡片后可直接进入。
- FCM 仅用于提醒，不再决定房间是否可发现；通知被拒绝、token 缺失或推送失败时，对方仍可从首页进入。
- 每个 pair 同时只有一个活跃房间；新房间覆盖旧房间。房主离开、记录过期或好友解绑后立即不可见。
- Account Worker 只保存加密访客邀请 URL，不保存 host key；读取必须命中当前活动 pair，创建者和第三方都不会获得加入入口。
